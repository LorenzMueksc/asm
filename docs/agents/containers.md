# Containers, processing, Event rpc, errors

Code: `container.go`, `node.go` (start/open/close), `node_grpc.go` (`Event`, `sendToContainer`).

## Model
- Not pooled [U]: every life is a new `Container`; a stale pointer only reaches its closed life (`ErrContainerClosed`). `ResetContainer` is for `NewContainer` containers (tests).
- Count capped by `n.sem` (`WithMaxContainerCount`, default 100). Node containers read the committed bitmap and published transitions through atomic pointers (`bitmapP`, `transitionsP` → `publishedTransitions`: `list()` by priority, `forEvent(name)`); `NewContainer` ones use their own `bitmap`/`transitions` (indexed once).
- `containerProcessing` = one life (`eventsC`, flags, pending, lazy `doneC`); replaced, never mutated. Node code closing containers captures `c.containerProcessing` under the map lock and calls `p.close()`.
- Options passed to `StartContainer` override the node's hooks (node hooks prepended, `withNodeHooks`).

## Lifecycle [U]
- `Close()`, ctx cancel, `DeleteContainer`, `Shutdown` only send a close signal. The container keeps accepting until `pending == 0` (no queued events, running work or batch timers).
- Goroutine on demand [U, 2026-10-24]: no goroutine for an idle container. `start(ctx, closedF)` (from `openContainer`; tests call it on `NewContainer` ones) stores ctx, `context.AfterFunc(ctx, requestClose)`, sets `runner`. Whoever makes work visible calls `schedule()` afterwards (`Event` after the send to `eventsC`, `sendTracedError`/`lateError`, `requestClose`, `donePending` when a closing container became idle): starts `run()` unless `running`, `closed` or not started. `run`: one event, the queued errors, `stopAccepting` → `closeIdle` + stop the ctx watch + `closedF`; nothing queued (`hasWork`) → waits up to `keepAlive` [U: node option `WithContainerKeepAlive`, default 5ms, 2026-10-24] on `eventsC`, `wakeC` (cap 1; `schedule` wakes a running goroutine for errors/close, `scheduleEvent` doesn't: the wait covers `eventsC`) or its timer (`keepAliveTimer`, one per container, made by the first goroutine [A 2026-11-12]: armed at a goroutine's first wait, not reset per event: on firing re-armed for the rest of `keepAlive` since `lastWork`); then `stopRunning(timer)` (under `lifecycleMu`: no events, errors, or idle close → stops the armed timer, so the next goroutine finds it stopped, `running = false`, return). After a round event no wait: the goroutine ends at once when idle (`rounds.md`). Goroutines start from `runF` (`c.run` bound once in `start`), no closure per start. A round dispatch worker may run the container in place of its goroutine for one round event (`claimRun`/`releaseRun`, `rounds.md`). Batch timers keep their own goroutine under `c.mu`. Flags `closeRequested`, `running`, `closed` under `lifecycleMu` (lock order `lifecycleMu` → `errMu`). `c.ctx` carries the `containerProcessing` (`closeRequestKey`): waits outside the container (hand-over slot) end on its close request (`closeRequestedOf`, `closingC` closed in `requestClose`). Counter `events` (accepted by `Event`, until the processing pass ended; `endPending(true)`) = `busy()`.
- Context [U, 2026-10-24]: each container gets `context.WithCancel(n.ctx)` in `openContainer`, cancelled by `closedF` after closeIdle (and its late errors).
- `closeIdle` order: stop accepting → `flushBatches` → closeF → close `eventsC` → `status = closed` → `removeF` (removes from node map, `endLock`) → `markDone` → report errors queued meanwhile.
- `done()` returns `doneC`, created on the first call (`closedC` once already closed); `markDone` closes it if created. `closedF` cancels the ctx and frees the slot. `Event()` returns `ErrContainerClosed` once not accepting. `StartContainer` waits on `done()` of a closing container, then starts a new one.
- Per life allocated lazily: `states` (`setState`), batch maps, `doneC`. Logger: `containerLogger` (`WithLazy`; a logger that logs nothing is reused). `forwardF`/`nodeErrF` are the node's bound once (`n.forwardF`, `n.failureF`). `openContainer` allocates the container and its `containerProcessing` together and uses `resetContainer` (no `removeF`); public `ResetContainer` sets one. The node's hooks are applied once (`hookOptions`, `containerOptions`).
- Containers close only via `Close`, `DeleteContainer`, `Shutdown` or close-after.

## Processing [U]
- Container goroutine and batch timer callbacks serialize on `c.mu`.
- Batch queues/timers keyed by transition name (queue stores the transition): published transitions are replaced on every change. A stale timer (not in `transitionTimers`) does nothing.
- Done channel (`WithDoneChannel`) fires once per event: after every matching transition incl. batches, or at once if nothing matches (`containerEvent.refs`). The send blocks: use a buffered channel.
- rpc-sent events carry `closeAfter`: the container closes itself once the event is released (forwarded: right after the pass). [U 2026-10-31] Not a container a `StartContainer` caller holds: `containerProcessing.held`, under `lifecycleMu`, set by `hold()` in `StartContainer` and checked at close time by `requestCallClose` (`processRemote`, `releaseEvent`), so a holder that got the container while the call ran keeps it open. [A 2026-10-31] A call's close signal sent before `hold()` (`closeByCall`: only calls sent one) makes `hold()` fail: `StartContainer` waits for that container to close and starts a new one. Other close signals (`Close`, `Shutdown`, ...) keep the old behaviour (returned, still closing). Containers opened internally (calls, `openPending` of hand-overs) still close once idle; checking "loaded" instead broke hand-overs, whose drain loads the container `openPending` opened (before: a joined call closed a holder's multi-step container between its events, found in econsim).
- `c.Emit(ctx, event, payload, opts...)`: nested in the calling transition (`runEvent` under held `c.mu`), only with the transition's ctx (`transitionCtx` marker from `executeActions`, else `ErrNotInTransition`), ≤ `maxEmitDepth` 16. A waited emit to a node already in the lend chain fails (cycle).
- Target calls [U: same-entity calls, shared DB, reply payload, deadlock-checked; 2026-10-24] [A: API, local only]: `Emit` with `WithTarget(id)` → `emitToTarget` → `targetF` = `Node.callTarget`: a `remoteExecution` with `otherEntity` (own func + state transitions of the entity, no remote ones) in the target container on this node. Waited (`targetCall`): `callContainer` with the caller's wait path (join if open here, else acquire; lock table refuses cycles), no wait path or `WithSkipRaft` → `sendToContainer`. Not waited: `acceptHandOver` without id (queued per id, `acquireAsync`). `c.Reply(ctx, v)` sets `remoteExecution.reply` of the calling events' parents (`ErrNoCaller` if none waits); read after done. Target = own id → error. A target transition owned by another node isn't run (no remote transitions on receivers). `c.Reply` also answers waited forwards (`forwarding.md`). `WithOnBusy(OnBusyFail)`: `ErrBusy` instead of waiting for a busy target (`locks.md`, Busy targets); a container is busy while `containerProcessing.events` > 0 (`busy()`).
- `c.HandOverId()` [U: no ctx, 2026-10-31]: id of the hand-over `processRemote` runs right now (its transitions and the save after them), "" otherwise; for idempotent writes of at-least-once hand-overs (`forwarding.md`).
- Reentrant containers [U: interleave at waits, node + container option, calls back run, not during lent calls, not busy while serving, metric + normal traces, no extra depth limit; 2026-10-31] [A: details]: `Container.reentrant` (`reentrance{on, events}`) from `containerOptions.reentrant` (node default `WithReentrant` added to the hooks, `WithContainerReentrant`/`WithContainerNotReentrant` override). A waited target call (`emitToTarget`) or waited forward not lending the lock (`lendsLock`: no matched remote transition of this entity) of a container holding its own lock (`serving`) runs the call on a goroutine (`waitServing`) while the container's goroutine, still holding `c.mu`, takes events from `eventsC`: allowed ones (`reentrance.runs`) via `processEventLocked(c.ctx, ...)`, others to `containerProcessing.deferred` (run first afterwards, `takeEvent`, counted by `hasWorkLocked`). The reply wins over the next event. `parked` counts waiting transitions (`busy(r, event)`: events > parked while the event runs meanwhile). Nested state: `callEvents` restored by `executeActions`, `handOverId` restored by `processRemote`. The forward's chain and trace are taken before the goroutine starts. Batch timers wait for `c.mu` as before; close and errors stay with the run loop.

## Hot path allocations [A 2026-11-12, A12; pure optimizations unless noted]
- Options: `WithDoneChannel`, `WithTarget` (one small struct each), `WithWaitRemote`, `WithDeferred` (shared values,
  `flagEventOption`) are types of their own; `Event`/`Emit` apply them by type (`applyEventOptions`), so their
  `eventOptions` stay on the stack; any other option is applied, with the ones after it, to a heap copy.
  `containerEvent.opts` (never read) is gone, so the variadic slices stay on the caller's stack.
- Transition ctx: the funcs of events run on `c.ctx` (mailbox, rounds, batch timers) get `c.txCtx`
  (`transitionContext`: `c.ctx` + `transitionCtx`, one per life; checked before the ctx chain walk). The ctx value is a
  `*transitionCtx` (no boxing). Nested `Emit` (depth + 1) and other ctxs still get a `context.WithValue`. QR17: the
  ctx is shared by the transitions of a life.
- `executeOrQueue` runs a single event as `evt.one()` (slice backed by `containerEvent.single`), `executeActions`
  builds the payload slice only for remote transitions and funcs batching events (`payloadOf`).
- `debugOn(logger)` guards the hot `debugf` calls: `debugf`'s arguments are boxed even when nothing is logged.
- Goroutine start from `runF` and the reused keep-alive timer (Lifecycle above). `tablesOf` recent cache (`state.md`).
- Measured (`BenchmarkLocalEvent`, details `testing.md`): 18 → 8 allocs, 660 → 406 B, ~3.0 → ~2.6 µs per event.

## Rounds [U 2026-11-12]
- Deferred events, round barrier, round batches, spawn and close: `rounds.md` (decisions QR1-QR17 in
  `docs/questionnaire.md`). Hooks here: `Emit` (`WithDeferred` → `emitDeferred` before the event is built, next to
  `checkReadOnlyEmit` for events without target; a reader's deferred `Emit`, `Spawn`, `CloseAfterRound` → `ErrReadOnly`),
  `processEventLocked` (payload `*roundRun` → `processRound`, after the init func; other events clear
  `round.current`/`currentMsg` while they run, for `MessageOf`), `executeOrQueue` (`roundBatch` → `queueRoundBatch`,
  without `refs++`; a full batch stopping its timer → `runsOn(-1)`), `startBatchTimer` (`runsOn` ±1 for
  `ErrRoundOverlap`), `actionFailed` (`round.failed`), field `Container.round`; node: field `Node.rounds`,
  `resetContainer` (`round.reset`, `setSpawnEntity`), `compileTransitionLocked` (`checkRoundBatch`), node_forward.go
  (`enqueueForwardedLocked`, `giveUpForwarded`, the done goroutine of `drainForwarded`: `runsOn`). Round events are
  ordinary mailbox events (writers, `lockWrite`); entity writes of rounds only happen under the processing lock or
  before the container is published.

## Reader and writer transitions
Code: `rwmode.go` (hooks in `container.go`: `lockWrite`/`unlockWrite` around `c.mu` in `processEvent`, `handleError` and batch timers, `initDone` after the init func, `dispatchRead` and `errNotRead` in `Event`, `checkReadOnlyEmit` in `Emit`, `withoutReadSlot` in `emitToTarget`, `applyState` in `executeActions`, `sharedEntity` in `releaseEvent`/`storeSnapshot`, immutable `mergeInto` in `forward`; `rwIndex` in `publishedTransitions`; `rw.newBuilderF` and `rw.setMode` in `NewContainer`/`resetContainer`; `readsCall` in `callContainer`).
- Rule [U, 2026-11-12]: per container any number of readers run concurrently with each other and with at most one writer; writers never overlap; a reader started during a writer sees the entity as it was before the writer started (copy-on-write publish).
- Modes [A]: `WithReadOnly()` marks a func transition (`Transition.ReadOnly`, local, not synced, not in the signature). An event is a read event if every transition of its name is a read-only func transition of the node that doesn't batch (`readOnlyFunc`; `rwIndex.direct`); for executions of other containers on the container's own lock (target calls, other entities, hand-overs; not lent ones, they carry the caller's entity) remote transitions are ignored (`rwIndex.executions`). Anything else is a writer: a state transition, a writer or remote transition of the same event, `WithBatching` > 1. Read-only transitions of an event a writer emits run inline in the writer.
- Dispatch [A]: `Event` hands a read event to `dispatchRead` before the mailbox: own goroutine (`runRead`), pending but not counted in `events` (never busy; `Container.busy` shadows `containerProcessing.busy` and returns false for read executions). Not started yet, or a writer runs that took no copy (it began before the node had read-only transitions): mailbox, runs as a writer.
- Publish [A]: `containerProcessing.pub` (per life). `lockWrite` sets `writing` and copies the builder's entity (`copyEntity`: `CloneMessageVT`, `proto.Clone`, shallow for fakes) unless the copy is fresh; only with read-only transitions and once the init func ran (else `initDone` copies right after it). `unlockWrite` marks the copy stale. A reader takes the fresh copy, or copies itself while no writer runs; before the init func ran it runs it as a writer (`lockWrite` + `runInit`); during a writer's init it waits on `pub.changedC`. Cost: one copy per writer pass in containers whose node has read-only transitions, none otherwise (immutable mode: none).
- Immutable-entity mode [U 2026-11-12: Q28 a, Q29 a, as built]: `WithImmutableEntity()` (container), `WithImmutableEntities()` (node default, appended to the hooks via `containerModes`: containers the node opens for calls, hand-overs, lent executions get it too). Contract: writers never change the entity in place, they `Set` a new one (may share unchanged nested messages). `publishLocked` stores the builder's entity itself, also without read-only transitions (free; the check needs it); reader views carry the flag. Copy-first: state transitions (`applyState`), a waited forward with one result (`mergeInto`). Pointer instead of clone: `releaseEvent`'s result and the trace snapshot (`sharedEntity`). Still one copy: per state transition, per waited-forward merge, the receiver's working copy of a lent forward (`ForwardEvent` is node code without the container's mode; `changedState` writes the decoded sent entity). The save func sees the pointer readers get next. No entity in the raft log, WAL or node snapshot. Copies are counted [U 2026-11-12, Q33 b]: `countCopy` (from `copyEntity`, `sharedEntity`) adds one to the node's `asm_entity_copies_total` (`nodeMetrics.entityCopies`, atomic; nil metrics without a node) and calls `entityCopyHook` (specs). Immutable mode keeps it at zero on the round path.
- Mutation check [U 2026-11-12: Q30 a, as built]: `WithImmutableEntityCheck()` (node option, via `containerModes`; only immutable containers): `sumLocked` fingerprints the published entity when a writer begins or its init func loaded it (`fingerprint`: deterministic encoding, fakes a shallow copy for `reflect.DeepEqual`), `unlockWrite` compares (`changedSince`) and sends `ErrEntityMutated` to the error func. Not covered: batches flushed at close (`flushBatches` takes `c.mu`, not `lockWrite`), readers changing it (`-race` finds those), entities that don't encode.
- Reader cap [U: `WithMaxReaders(n)` container option, 0 or unset = unlimited, a read event beyond it waits for a slot, no error, no busy; 2026-11-12] [U 2026-11-12: details as built, Q32 c]: `rw.slots` channel per life (`setMode`); `runRead` takes a slot before `readEntity`, a waiting reader keeps its goroutine, the event metric starts after the slot. A reader gives its slot back while it waits in `emitToTarget` (`withoutReadSlot`; the only place a reader waits for other containers): else a read call back would wait for slots held by readers waiting for it. Node default `WithMaxReadersPerContainer(n)`: appends `WithMaxReaders(n)` to `containerModes` (the node's hooks), so the containers the node opens itself (calls, hand-overs, lent executions) are capped too; a container's own `WithMaxReaders` comes after the hooks and overrides it (0: no cap).
- Read call-backs [U: the lock table knows modes; a waited call back into a container whose writer waits for the caller runs when the event is a read event, only writer-vs-writer cycles deadlock; 2026-11-12] [U 2026-11-12: mechanism as built, Q31 a]: `callContainer` joins an open container with `read` when `readsCall` (`rwIndex.executions`), the lock table records the call without wait edges (`locks.md`). It must then run as a reader (`withReadCall`): otherwise `Event` returns `errNotRead` and `callContainer` calls again as a writer, deadlock-checked.
- Reader view [A]: `readerView` = new `Container` sharing `containerProcessing` (errors, `Event`, close) with its own builder (`rw.newBuilderF`, set to the copy), states, callEvents, routing cache, the classified transitions (`transitions`, no `transitionsP`), no lifecycle funcs (save ignored), no lock token (the reader holds no lock: its calls carry only its callers' wait path), not reentrant, `rw.base` = the container. Runs `runEvent`/`processRemote` unchanged; `endRead` replaces the final `releaseEvent` (no entity result: nothing changed).
- Reader may [A]: read (never change the copy: shared with other readers), `Reply`, `Emit` with `WithTarget` (waited or not), `Emit` read events of its own container (inline on the same copy), `c.Event`. Other `Emit` without target, a deferred `Emit`, `Spawn`, `CloseAfterRound`: `ErrReadOnly` (`rounds.md`). `Set` on its builder is dropped.
- Reentrancy [A]: unchanged for writers (`waitServing` interleaves writer events of the filter while a writer waits; their changes are published with the waiting writer). Read events never reach the mailbox, so they run during any writer, also in a container that isn't reentrant, and need not be listed in `WithContainerReentrant`. Reentrant events stay writers [U 2026-11-12].
- Limits [A]: a writer call back into a container whose writer waits for the caller is refused (`ErrWouldDeadlock`) as before. Copy mode costs one copy per writer pass: use immutable mode for large entities.

## Event rpc
- Container id from `WithContainerIdFunc` (none → `FailedPrecondition`, empty → `InvalidArgument`). Payload via `anypb.UnmarshalNew` (unknown → `InvalidArgument`).
- `meta["wait"]="true"` waits for done (or request ctx); otherwise fire-and-forget, request ctx only bounds waiting for the lock. `ErrContainerClosed` → retries `StartContainer`.
- Public listener (`WithPublicAddr`) and TLS rules: `security.md`.

## Errors
- No dependency on the former shared module. Log errors with `%+v`. Debug messages with args via `debugf` (formats only if debug enabled).
- Container errors are queued (`sendError`: `errs` slice + `schedule`; none dropped) and handled by `run`: logged, `errorF` under `c.mu`; non-nil return → `requestClose`. Close func errors arrive after the container closed.

## Gotchas
- `Close()` inside a transition or the error func deadlocks (waits for itself). `c.Event(...)` inside a transition is fine unless `eventsC` (buffer `maxInFlight`, default 10) is full; it runs after the current event.
- `StartContainer` inside a transition to wait for another container can deadlock: use `Emit` + `WithWaitRemote()`.
- Handing over at the limit (`WithMaxPendingHandOvers`) blocks the transition until a hand-over ran, bounded only by the container ctx: an open container handing over ≥ limit work for its own id waits forever (`forwarding.md`).
