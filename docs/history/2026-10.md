# History 2026-10 (archive)

Verbatim copy of plan.md as of 2026-10-23: detailed change notes, decisions, measurements. Agents: read only when you need the reasoning or numbers behind a past change.


Changes made to the ASM repository, and work still open. Only v2 exists; v1 was deleted on 2026-10-23.

## Done (2026-10-21)

### Major changes

- **Repository layout:** v1 moved from the repository root into `v1/`, so v1 and v2 now sit side by side. v1 is frozen.
- **Builds standalone:**
  - Removed the dependency on the former shared module. Errors are now logged with `%+v`, which keeps stack traces.
  - Removed v2's import of the v1 package; v2 now uses its own `Bitmap` and `Dependencies`.
  - Ran `go mod tidy`, which added `go.sum`.
- **State model:** replaced the old state apply function, which was called as `(bm, s, s)` and changed nothing, with `mergeState`. It replaces bits per property.
  - Old bits no longer pile up.
  - Moving backward (completed to pending) works.
  - Event bits are merged first, then entity bits, so the entity wins.
  - Zero values in a state transition target are applied.
  - The old state apply function and `getHighestDefinedBit` were removed.
- **v2 state transitions:** they used to be ignored silently; `AddStateTransition` now works.
- **v2 container lifecycle (close when idle):**
  - A close signal no longer stops the container right away. It keeps accepting events until nothing is queued, running or waiting on a batch timer.
  - Once idle, it stops accepting, runs waiting batches, runs `closeF`, closes its channels, removes itself from the node map and goes back to the pool.
  - `Container.Event` returns `ErrContainerClosed` once the container has stopped accepting. **This is an API change.**
  - `StartContainer` waits for a closing container and then starts a new one.
  - `DeleteContainer` and `Shutdown` go through `Close()`. This fixes a deadlock: `Shutdown` used to hold the map lock while closing.
- **v2 batching race:** the timer callback and event processing now share one mutex. Timers are tracked so a stale timer does no work. Batches without a period run on close.
- **v2 done channel:** fires exactly once per event, after all matching transitions (batches included). It also fires when nothing matches.
- **v2 `Event` rpc implemented** (it used to be `panic("implement me")`):
  - The container ID comes from the new `WithContainerIdFunc`.
  - The payload is decoded with `anypb.UnmarshalNew`.
  - `meta["wait"]="true"` waits for processing. Otherwise the rpc returns right away.
  - The container always gets a close signal after the event.

### Minor changes

- v2: the container goroutine no longer spins on an already-cancelled context. This was the cause of the 2 failing done-channel specs.
- v2: the raft ready loop returns after stop. It used to close `errorC` again and panic.
- v2: `Join` checks that the `node_id` metadata is present before reading it.
- `getFieldByJsonName` matches json tags without `omitempty`.
- `v2/README.md` was rewritten to match the actual protos, paths, API and semantics.
- New tests: `v2/container_lifecycle_test.go`, `v2/node_grpc_test.go`, and `mergeState` tests in `v2/bitmaps_test.go`.
- v1 got the same bug fixes before it was frozen (state merge, nil-timer panic, timer double run, `Transitions()` nil entries, sha1 hash, queue cycle).

## Done: cluster sync (2026-10-21)

Goal: a container's state means the same entity values on every node, transitions are known cluster-wide, and remote transitions run on the node that owns them.

### Major changes

- **Protobuf tooling:**
  - Installed protoc 36.0 (winget), `protoc-gen-go@v1.36.5` (matches the runtime) and `protoc-gen-go-grpc@v1.5.1`.
  - Regenerated `service/`.
- **Proto changes:**
  - Removed `EventRequest.options.close_after` and `JoinRequest.transitions`.
  - `NodeEventType` keeps only `BITMAP_ADD`; removed `NodeLog.containerId` and `NodeLog.meta`.
  - New `Bits` message. `Bitmap.BitValue.bit` became `index`. Condition states use `Bits`.
  - `Transition` got `batching`, `signature` and the target `state`.
  - New RPCs: `GetTransitions`, `AddTransitions`, `ExecuteTransition`.
- **Bits instead of int:**
  - State, conditions and targets are a packed bitset (`[]uint64`); a new word is only added when needed.
  - `BitValue.Bit` (mask) became `BitValue.Index`.
  - There is no 64-value limit anymore.
- **Bitmap shared through the raft log (append-only):**
  - Each node proposes its local root entity bitmaps.
  - The first committed definition is adopted; later ones append missing values with the next free index, walking children in name order.
  - Conflicts fail the proposing node.
  - Values are encoded as wrapperspb types.
  - Containers use the committed layout.
  - Container start/close entries are no longer logged.
- **Node startup:**
  - `NewNode` is non-blocking, with `Ready()` and `Err()`. A failed node stops.
  - `StartContainer` returns `(*Container, bool, error)` and blocks until the node is ready. **This is an API change.**
  - `Container.Event` returns the node's failure.
- **Transitions:**
  - Conditions and state targets are compiled against the committed layout, and again when it changes.
  - Signature = event name + conditions + action. The func is identified by its runtime name, or by `WithFuncKey`.
  - Same name + same signature = load-balanced owners. A different signature fails the introducing node.
  - Synced with direct RPCs: pull and push when ready, push on runtime add. Owners leaving the cluster are removed.
  - The published transition list is copy-on-write.
- **Remote transitions:**
  - The sender evaluates the synced conditions, prefers local execution, and otherwise picks a random reachable owner.
  - The sender does the batching.
  - The owner runs only the target transition and returns its entity.
  - New event option `WithWaitRemote()`.
  - State transitions synced from other nodes run locally.
- **Raft fixes:**
  - A joining node starts with `RestartNode`.
  - `propose` no longer campaigns when there is no leader.
  - Peer maps are locked.
  - Sending to an unknown peer no longer panics, and sends have a timeout.
  - A failed node stops the raft loop and the gRPC server.

### Minor changes

- Nested structs are modified in place by state transitions; a new one is only created when the field is nil.
- Cleanup:
  - Removed `containerStatusIdle`, `containerProcessing.proposeC` and the `logsC` parameter of `NewContainer`.
  - Removed `WithRemoteRetention`.
  - `WithRemoteEntity`, `WithRemoteContainerId` and `WithOnlyLocal` were replaced by internal forwarding.
  - `Transition.Remote` and `NodeIds` are used for synced transitions.
- Batch queues are keyed by transition name, because published transitions are replaced on every change.
- Errors of a transition executed for another node are returned to the sender (`codes.Aborted`).
- Fixed rare crashes from pool reuse (`sync: unlock of unlocked mutex`). They happened when a container closed and was reused while someone else was still closing it:
  - `closeOnce` now lives in the per-life `containerProcessing`, which a reset replaces. `Shutdown` and `DeleteContainer` capture that life while holding the map lock.
  - Events from the RPC handlers carry an internal close-after flag, so the container closes itself instead of being touched after its event is done.
- New tests: `bits_test.go`, `bitmap_layout_test.go`, `transitions_test.go`, `cluster_test.go` (2 real raft nodes on localhost, label `cluster`).
- Multi-node tests in `cluster_multi_test.go`:
  - 3 nodes: one layout built from all configs, every node knows every peer, transition sync and forwarding between followers, skipping an unreachable owner, a new leader after the leader stops, and joining through the new leader.
  - 5 nodes: load balancing between 3 owners, and 4 nodes joining at the same time.
- Fixed nodes joining at the same time: raft drops a configuration change proposed while another is pending, but `Join` still answered success, so the dropped node waited forever. The leader now serializes joins, and each `Join` waits until the node is applied as peer, proposing again if dropped (30s timeout).
- `v2/README.md` is regenerated from the .proto files and documents the cluster behavior.

## Done: locking, compaction, demo (2026-10-21)

### Major changes

- **Container locking:** a container id is open on only one node at a time.
  - Leases in the raft log: new entry types `LOCK_ACQUIRE`, `LOCK_RELEASE` and `NODE_HEARTBEAT`. The log no longer carries only the bitmap.
  - Locks belong to nodes. A heartbeat every renew interval renews all locks of a node. A lock expires when its holder's last entry is older than the holder's lease (`WithLeaseTimeout`, default 10s/3s). Expiry is judged from the timestamps in the entries.
  - `StartContainer` acquires the lock and waits while another node holds it. Closing releases it, with tokens so that closing and reopening on one node keeps the lock.
  - A node that loses a lock after its lease expired closes its container.
  - Remote transitions borrow the lock. The sender blocks until the owner has finished, even without `WithWaitRemote()`, which now only decides whether the returned entity is applied. The owner checks the holder (`ExecuteTransitionRequest.holder_node_id`).
- **Log compaction:** after N applied entries (`WithSnapshotCount`, default 10000, keeping 5000), `CreateSnapshot` + `Compact` run.
  - The snapshot (`NodeSnapshot`) holds the bitmap, the peers, the locks and the heartbeats.
  - Lagging and joining nodes restore from `MsgSnap`, and the leader reports the snapshot status.
  - Memory only.
- **Demo `examples/gamemeta`:** 5 nodes as separate processes, started by a launcher with colored terminal output.
  - Nodes: 2 region gateways, matchmaking, store, anti-cheat.
  - Shows cluster forming, bitmap merging, transition sync, remote execution, and lock waiting on a player shared by both gateways.
  - The gateways share a file-based player store.

- **`StartContainer` ctx only bounds waiting** (node ready, lock, max container count). Containers run on a node-owned context, cancelled after the node stopped or failed. Containers close only via `Close`, `DeleteContainer`, `Shutdown` or close-after. **This is a behavior change:** cancelling the ctx no longer closes a running container. The Event rpc no longer needs its own container contexts.

### Minor changes

- More Info logs: committed bitmaps, nodes joining, transition sync.
- New tests in `cluster_lock_test.go`:
  - one node per id
  - waiting for a release
  - keeping the lock when reopening on the same node
  - taking over after the lease of a crashed node
  - rejecting remote executions without the lock
  - compaction with a joining node restored from the snapshot
- The `testCluster` harness can crash a node (stop raft and gRPC without closing containers) and takes extra node options.

## Done: handing over forwarded work (2026-10-21)

- Remote transitions without `WithWaitRemote()` are handed over completely instead of borrowing the lock:
  - The owner accepts right away and the sender continues.
  - The owner queues the work per container id, in order.
  - It runs it in its own container, which acquires the lock once the sender released it and loads the entity with the owner's init func.
  - It checks the conditions again, runs only the target transition, saves on change and closes.
- With `WithWaitRemote()` the sender still lends its lock until the response returns.
- New `ExecuteTransitionRequest.wait`. The entity is only sent when waiting. Holder verification only applies to lent locks.
- Tests in `cluster_forward_test.go` (shared in-memory store standing in for a database):
  - hand-over after release
  - skipping when the conditions don't match anymore
  - order
  - lending when waiting
- Open: handed over work is lost if the owner fails before it got the lock (in memory only).

## Done: error func, leaving the cluster, raft send retries (2026-10-22)

### Major changes

- **Error func:** `WithErrorFunc` / `WithContainerErrorFunc` now receive every error of a container.
  - It runs on the container goroutine under `c.mu`, like a transition. Errors are still logged.
  - A non-nil return sends the container the close signal.
- **Leaving the cluster:**
  - `Node.Leave(ctx)` closes all containers, waits until they're closed, then gets the node removed and stops it without an error.
    - From then on `StartContainer` returns `ErrNodeStopped`.
    - A leader hands its leadership to the most up to date peer first.
    - If ctx ends first, it returns the error and the node stays a member.
  - Closing the stop channel runs `Leave` (30s timeout) and stops the node even if leaving fails. The stop channel of the user is no longer the internal `stopC`.
  - `Node.RemoveNode(ctx, id)` removes another node (eg. a crashed one) through the leader, using the new `RemovePeer` rpc.
  - Applying a removal frees the removed node's locks right away, drops it as transition owner and rejects its messages and proposals with `PermissionDenied`.
  - A removed node stops when it applies its own removal or gets `PermissionDenied`. It doesn't rejoin by itself.
  - A node can join again with an old id. `JoinResponse.added_index` lets it ignore the replayed removal of the earlier node with that id.
  - Removed ids are kept in `NodeSnapshot.removed`. Restoring a snapshot now replaces the peers instead of merging them.
- **Raft send retries:** one sender goroutine and queue per peer (`node_send.go`), so the ready loop no longer blocks on gRPC.
  - A failed `Sync` is retried 3 times with backoff, then reported unreachable and dropped.
  - Queued batches are merged into one request (up to 2 MB).
  - This is the "send in parallel" half of the planned performance item.

### Minor changes

- Container options passed to `StartContainer` now take precedence over the node's hooks. Before, the node's hooks were appended last and always won, even when nil.
- Tests:
  - `node_test.go`: error func, leaving without raft, stop channel.
  - `cluster_membership_test.go`: leaving follower, leaving leader, removing a crashed node through a follower, removing a running node, stop channel plus rejoin with the same id.
  - The harness has `forget(id)` and `peerIds(n)`, and `start` resets the stopped/crashed flags of a reused id.

## Done: the receiving node decides (2026-10-22)

### Major changes

- **Forwarded events instead of named transitions.** `ForwardEvent` replaces `ExecuteTransition` (proto change). The node receiving a forwarded event runs its own func transitions matching it, with its own condition evaluation, except the ones in `exclude`.
- **Sender:**
  - It runs its local transitions first.
  - It then uses the synced conditions only for routing, and batches forwarded events per event name (the largest batching config among the remote transitions of that name).
  - It routes each batch with set cover: the node owning most matched transitions first, random ties, unreachable nodes re-covered.
  - Unmatched remote transitions go to a picked owner, so the receiver can decide they match.
- **Exclude list:** every request excludes the func transitions of the event which run on the sender or in another request, so nothing runs twice.
- **Receiver:**
  - It passes the payloads one by one through its transitions: batching ones batch, the others run per event.
  - A receiver batch that isn't full runs when the forwarded container closes right after the request.
- **Waiting:** receivers are called in parallel. Their entities are merged into the sender's entity field by field against the sent entity (`mergeChangedFields`; the later response wins on the same field).

### Minor changes

- Removed `remoteExecution.recheck`, `executeRemote`, `localTransition` and `Container.actionErrs`. Errors of forwarded events are collected per request (`remoteExecution.errs`), also for batches that run later.
- Tests: `cluster_route_test.go` (5 cluster specs and a merge unit spec). The borrow spec in `cluster_lock_test.go` uses `ForwardEvent`.
- Not rerun: benchmarks.

## Done: priority order, matched nodes only, bits responses (2026-10-22)

- **Priority order:** remote transitions are forwarded at their place in the priority order. The matching remote transitions collected so far are routed together before the next local transition of the event is evaluated, so with wait it sees their result. A batched routing still joins its batch after the local transitions.
- **Matched nodes only:** remote transitions which didn't match on the sender are no longer assigned to a picked node; the exclude list covers them. Only nodes owning a matched transition receive the event.
- **Bits responses:** `ForwardEventResponse.changed_state` (proto change). A receiver returns only the bits of the properties it changed when applying them to the sent entity reproduces its entity exactly, otherwise the entity. The sender applies bits per property and merges entities field by field, then re-evaluates the state.
- Tests in `cluster_route_test.go`: only matched nodes, priority order across two forwards, bits vs entity responses.
- **Race detector:** gcc installed (WinLibs via winget). `go test -race` found 6 races, all in `container_test.go`: specs read `status` or closure variables after `time.Sleep` instead of waiting for `doneC`. Fixed in the specs; the production code never reads `status`. Fast and cluster specs pass with `-race`.
- **State after func transitions:** the entity is evaluated into the state after every func transition (also a failed one), so lower-priority transitions of the same event see its changes. Before, only state transitions and forward results updated the state within an event. Spec in `node_test.go`.

## Done: fair lock queue (2026-10-22)

- **Problem (demo):** a node could take back its own lock right after closing a container, before its release was committed, so a node waiting for the same id could starve.
- **Lock acquires are queued** in log order (`containerLock.queue`):
  - A released or expired lock goes to the first waiter whose node is alive at the entry's timestamp; expired waiters are skipped.
  - A holder asking again queues behind the waiters, or gets the lock back right away if nobody waits.
- **New `LOCK_CANCEL` entry** (proto change): a waiter whose ctx ends cancels its place. A cancel of a token already holding the lock passes it on. A lock handed to an attempt which already gave up is released by its node.
- Snapshots carry the queues (`NodeSnapshot.Lock.waiters`, proto change). A removed node is dropped from all queues.
- Tests:
  - `node_locks_test.go`: 6 lock table unit specs.
  - `cluster_lock_test.go`: the waiting node gets the lock before the holder gets it again; a waiter giving up lets the next one have it.
  - Full suite passes with `-race`.
- Demo (40s): every time the other gateway waited for `duo-zoe`, it got the lock on release (6 times); no timeouts.

## Fixed: demo saves on lent locks (2026-10-22)

- **Symptom:** after about a minute, a panic in `join_party` (nil player) and "no reachable owner for transition score".
- **Cause:** progression stored players with its close func, which also ran in its borrowed containers. Those close asynchronously, after the gateway may have stored and released the player. So it wrote stale players (eg. still `in_match`) or overlapped with a node reading the file. A failed load left the player nil, and the transitions dereferenced it.
- **Fix (demo):**
  - progression stores players only with its save func, after `score` (`WithSaveAfter`, handed-over work on its own lock);
  - the store writes atomically (temp file and rename);
  - transitions return an error instead of panicking when the player isn't loaded.
- 65s run: no errors, no stale player files.
- Decided afterwards: borrowed containers keep running init and save funcs (see the next section).

## Done: lock wake-ups, protobuf raft messages, lock token race (2026-10-22)

- **Wake only the waiters of the lock that changed:**
  - `lockTable.waiters` holds a channel per container id, created when somebody waits (`get`), and closed and removed on the next change of that lock (`changedLocked(id)`).
  - Liveness changes have their own lazy channel (`hasLiveness`, used by `waitForHeartbeat`). A snapshot restore wakes everyone (`changedAllLocked`).
  - Before, every lock table entry (also every heartbeat) woke every goroutine waiting for any lock.
- **Raft messages are protobuf:** `raftpb.Message.Marshal`/`Unmarshal` instead of `encoding/json`.
- **Bug fix, found by the benchmarks** (a session took 10s, a borrowed forward 5s):
  - `acquireLock` removed its token from the in-use set as soon as it was woken. But `lockChanged` runs after the wake-up in the apply goroutine, took the granted lock for an attempt which gave up, and released it.
  - The container ran on without its lock, and borrowed forwards then failed the holder check (5s timeout).
  - Now `lockTokens` keeps a token from the attempt until its release (`releaseLock`, `dropLockToken`).
- Benchmarks report the slowest operation too (`max-us`).

## Done: waited calls can't deadlock (2026-10-22)

The user asked to make sure the cluster can't deadlock while waiting across entities stays possible; the rest was left to the agent.

- Before: a waited call of another entity acquired the target container's lock like any start. A call back to a container waiting for it (player, match, player), or two containers waiting for each other's locks, hung until the sender's ctx ended. Borrowed starts also blocked for a container slot, which containers waiting for them could hold.
- Now the lock table is a wait-for graph:
  - Waited requests carry `wait_path` (lock tokens of the waiting containers).
  - Receivers of another entity acquire the lock with it, or join the open container through the log (`ContainerLock.join`). Locks record the running calls (`calls`), `LOCK_DONE` ends them.
  - An acquire that would wait for a container on its own path is refused deterministically on every node (`ErrWouldDeadlock`, `Aborted`). Only the call closing the cycle fails, the others go on.
- Waited starts don't wait for container slots or node-local starts anymore.
- Proto: `ContainerLock.wait_path`/`join`, `NodeEventType.LOCK_DONE`, `NodeSnapshot.Lock.Waiter.wait_path`, `NodeSnapshot.Lock.calls`, `ForwardEventRequest.wait_path`.
- The dev tool shows waited calls and wait paths on the locks page.
- Cost: a waited call of another entity commits one acquire (also when it joins an open container, which was free before) and one async `LOCK_DONE`.
- Specs: deadlock check unit specs (back reference, cycles in either order and through several locks, same caller queuing, join, done, release, cancel) and cluster specs (back reference, cycle through a joined container, repeated waited calls).
